# Bringing a GameCube decomp to life in the PC port (the decompiled code running natively): a playbook

This is how a matched (or nearly matched) GameCube decompilation of Pokémon Colosseum is made to run natively on a
PC, one screen at a time, written so another team (an XD decomp, another GameCube port) can follow the same path.
Claims are labelled **verified** (checked against the game's code or seen in a run) or **likely**.

## 1. The order of work, and why

| Step | What "done" means | Why this order |
|---|---|---|
| 1. **Compile** | every game, HSD and audio source file compiles with the PC compiler (GCC / MinGW) under `TARGET_PC` | cheapest step; it surfaces prototypes, intrinsics and inline assembly before anything runs |
| 2. **Link** | one executable links; whatever is still missing becomes a **logging stub** (generated) | the undefined-symbol list is the first honest measure of what the port lacks |
| 3. **Data in place** | the original program's data (tables, strings, pointer tables) generated as C from the disc's own bytes at build time, with pointers relocated | the game reads thousands of tables; hand-writing them is impossible and copying raw bytes is wrong (byte order, pointer size) |
| 4. **First boot** | `main()` runs: OS, heaps, disc, threads, sound, the module loader, the script engine; no crash for the whole time limit | crashes here are almost all data-layout bugs (section 2; *likely*); fix them before chasing visuals |
| 5. **Screen by screen** | logos → title → memory card → top menu → name entry → the opening → the first room → the first battle | each screen exercises a new subsystem; stopping at the first wrong screen keeps the bug list short |

Rules that kept this tractable: the **GameCube build stays byte-identical** through every PC change (PC code lives
under `#ifdef TARGET_PC` or in PC-only headers, and every commit is checked against the original checksums and the
per-function match report); **one heavy build or boot at a time** on the machine (section 4).

## 2. Bug families, how to recognise them, how to fix them

Almost every crash and wrong screen so far belongs to one of these families. Each has a fix pattern and, where
possible, a checker that finds the next case before it crashes.

| Family | How it shows up | Fix pattern | Checker |
|---|---|---|---|
| **Real code hidden by an automated declaration pass** | a feature silently does nothing in the PC port while its code looks right: the battle's "choose your next Pokémon" loop spun forever after a faint (no menu, no HP boxes), and item give / use got no Pokémon list, because the three calls that open the party menu (`MPO_RETURN menuPokemonOpenSub(...)`, a macro that expands to `return`) had been wrapped in `#ifndef TARGET_PC` by the pass that hides local prototypes (it read "WORD name(...);" as a declaration) (verified) | unwrap the statements; teach the pass that a parenthesised list with literals or expressions is a call | scan every `#ifndef TARGET_PC` "canonical prototype" block for statements (returns, assignments, calls, literal arguments); it found exactly these three; a thread-yield trace (which code each game thread waits in) found the spinning loop |
| **Big-endian disc data read natively** | absurd counts and ids (0x01000000 instead of 1), lookups that never match, a room id read byte-swapped so every room lookup fails (verified); a condition table's 16-bit "kind" read as 0x2A00 instead of 0x2A, so the battle never recorded "super effective" or "no effect" and an immune Pokémon still took a move's side effects (verified) | read through big-endian views: a `DISC_STRUCT` (GCC's `scalar_storage_order("big-endian")`) for records, `DISC_U16` / `DISC_U32` for raw reads; counts converted once at load where the code uses them natively | table-width scan (which getters return disc records); review of raw `*(u32*)(p + n)` reads of disc pointers. A disc record the game copies byte for byte into the save (the Colosseum rule record: three presets, copied with `memcpy`, "custom rules" detected with `memcmp`) stays big-endian in the save too, so its readers need the views wherever the record lives: the level floor of 1 read as 256 refused every Pokémon at Realgam Tower (verified) |
| **32-bit pointer slots in GameCube-layout records** | a list walk reads 8 bytes where the record has 4: garbage pointers in window / sprite lists, menu arguments, message tasks (verified); a small struct with four pointers embedded inside a bigger GameCube-layout record grows from 0x30 to 0x48 bytes, and resetting it overwrites the next fields: here a battle Pokémon's two types and ability, every turn, so every hit came out neutral (verified with a write-watch: a read-only page plus an exception handler that logs the writing instruction); a global block of initialised data sized for 4-byte pointers (24 bytes) viewed through a struct whose native pointers make it 40, so its list-head writes run into the next table (likely); a state block that opens with a pointer, which pushes every later field 4 bytes in the PC port while other code indexes the same block at GameCube offsets: collision objects' enable flags were read from and toggled in a neighbouring object's scale (likely); 8-byte reads of a 4-byte slot that take the next slot as the upper half, and 8-byte stores that wipe it (a menu scene's camera read with the camera position's first float glued on; likely) | keep the GameCube layout and make the field a 32-bit slot (`PTR32_FIELD`, read with `P32`, write with `P32_SET`; `PTR32_AT_T` / `PTR32_AT_SET_T` for raw offsets); keep everything the game sees below 4 GB so the values stay exact; add `_Static_assert(sizeof(T) == <GameCube size>)` in the PC port to every struct that overlays such memory | a slot-walk checker (native reads at known slot offsets in list walks; part of the gate); an audit of every struct with GameCube offset comments and a pointer member: where its memory comes from (its own `sizeof` allocation is safe; embedded, sized by a GameCube constant, defined with the GameCube size, or read elsewhere at raw offsets is not) |
| **Views of one record that disagree on its layout** | one function reads a GameCube-layout record (32-bit slots) through a private struct with native pointers: a menu model's teardown read the letters of the player's name as a light pointer (verified); the PC box screen's grid window, viewed through a struct whose window argument slot (+0x60) was a native pointer, so its cursor function read the cursor 4 bytes late and never made the "slot to box bar" jump: the same presses withdrew a Pokémon where the console deposited three (verified: with a 32-bit slot the deposits land on the console's exact frames); a menu's work area filled at GameCube offsets with 4-byte sprite slots and a 4-byte entry array, but read through a struct of native pointers, so most fields were read past the allocation, and the entry pointers were stored 8 bytes wide into an array of 4-byte cells that is then sorted with element size 4: a heap overrun (likely); a battle-intro screen whose state is read at GameCube offsets almost everywhere but through a struct with one native pointer in one place, so the trainer pictures and timers the two halves exchange land at different addresses (likely); a scene that reads a model's field through an unrelated struct that happens to have the same GameCube offset but not the same PC offset (likely); a model object that is a native struct in the PC port read at its GameCube byte offset (+0xE4 for its part-animation slots), so an NPC's head-turn was registered inside the texture-animation fields (likely); an aura effect took a native model's +0x08 as its joint (the resource record in the PC port) and wrote the joint's scale and translation at the GameCube offsets (likely) | every view uses the same slot types (`PTR32_FIELD`); search for every private struct over the same global; read an object through its real type, never through a struct that only matches on the GameCube; a native struct is never read at raw GameCube offsets (use the field, or an `offsetof`-based constant in the PC port) | grep for local `typedef struct` views of the same symbol; a `_Static_assert` of the GameCube size on each view; for each native struct, a sweep of raw offsets through variables that hold one (named like it, assigned from a call that returns one, or passed to its functions); intersect any such list with the PC binary's debug line table (`objdump --dwarf=decodedline`), which names exactly the source lines the PC build runs, so branches and copies it never compiles drop out (98 suspects became 4 live sites) |
| **Pools allocated as count × the GameCube record size** | the engine's thread pool was allocated as 20 × 0x24 bytes, but the PC thread record (two links and an entry pointer, 8 bytes each) is 0x38: only the first 13 records fit, and the rest lay in the next heap block, the graphics request buffer (verified: the heap's allocation order puts the two blocks exactly side by side). Such an overlap stays silent until enough threads exist at once | allocate `count * sizeof(record)` in the PC port | grep allocator calls whose size is `count * 0x..`, and check whether the records are read through a C struct that holds pointers (raw byte offsets are safe) |
| **One-byte flags poked at GameCube offsets** | a "block this thread" helper set its flag as `p[0x9] = 1`; in the PC port byte 9 of the record is the second byte of an 8-byte link, so blocking a room's script threads at a room change turned a valid link 0x8049EBB0 into 0x804901B0, and the scheduler later walked into unrelated memory (verified with a hardware write-watch on the link) | set the flag by field name in the PC port | grep `u8*` parameters and `p[0x..]` writes in functions that receive a record a C struct also describes; a per-frame scan of the pool's links found the damage, the write-watch found the writer |
| **Two views of one memory block with different sizes** | one file allocates and walks a pool with the GameCube size, another with the PC size: a thread pointer of 0xFB13 when a room unloads (verified) | one size for both views in the PC port, tied together with `_Static_assert`s | the static asserts; grep for second structs over the same allocation |
| **Getters that read a struct at a GameCube offset** | `*(u32*)(ctx + 0x4)` reads the upper half of a native pointer: every room's setup jobs were filed under id 0, never released, and old rooms' setup functions ran again in later rooms (verified); a model's bounding box holds three pointers before the box, so in the PC port the box sits 0x10 bytes further in, and the battle camera read the box's minimum, maximum and size at the GameCube offsets: every procedural shot was framed from about a fifth of the real height, the low "side profile" shots (verified by logging the camera's computed parameters on both sides) | read the field by name in the PC port, or use per-platform offset constants checked against `offsetof` | grep for raw offsets into structs that contain pointers; log the values the code computes from the struct on both sides and compare |
| **A value type that grew in the PC port, used as the stride of 4-byte data** | a script VM's value union held a `char*`, so every value was 8 bytes in the PC port; the values on the VM's own stack were fine, but a script's globals are 4-byte words inside the script file, read and written through the same union: global n landed at globals + 8n, and writing the later globals overwrote the script's code after them. A cutscene thread hit a zeroed sleep call, slid over the zeros onto an operand byte that reads as "exit", and the scene stopped before its first line (verified with a hardware write-watch on the code bytes and an opcode trace) | keep the union at its GameCube size (store addresses as 32-bit values, convert at use), with a `_Static_assert` on its size | for every union or struct that overlays file data or is indexed as an array of file words, check that its PC size equals its GameCube size |
| **Native C data tables with pointer members, read in GameCube-sized steps** | a table written as C initialisers with a pointer member (one 16-byte record per name-entry kind) becomes 24-byte records in the PC port, but the code indexes it with GameCube byte offsets (`table + 4 + kind * 16`): the second kind read its maximum name length from padding (0), and the first letter typed went one cell before the name buffer, over a model's light pointer (verified with a write-watch) | give the table its GameCube record size in the PC port (the pointer as a 32-bit slot, filled at start-up) and convert any struct readers of it | list hand-written data tables whose struct has a pointer member, and check how every reader indexes them |
| **Data addressed past the end of its symbol** | the GameCube compiler reaches neighbouring data as `base + offset`; in the PC port each symbol is its own array, so the read lands elsewhere: a name-entry table at +0x88 from a 12-byte symbol gave a bogus model id and a black screen (verified) | map `base + off` to the symbol that really holds that address, under `TARGET_PC` | a past-the-end checker (offsets beyond a symbol's size, including through local aliases) |
| **Scripts that carry GameCube addresses in their bytes** | battle scripts jump to addresses stored inside the script bytes and run across symbol boundaries (likely; not yet reached at run time) | planned: keep raw script regions at their GameCube addresses in the PC's memory map | none yet |
| **Leftover-register and wrong-arity calls** | the original code passes a value in a register the C prototype doesn't list; in the PC port that argument is garbage. A quieter shape (verified, 2026-10-30): a decompiled function written as `f(void)` that passes uninitialised locals named `r3` / `r4` to its callee, because on the console its own first arguments are still in those registers; ten battle-AI "would this move work" checks had it, so in the PC port the AI kept using a move whose effect was already active | read the real value from the original assembly; never default to 0; flag it for checking against the emulator when the assembly can't settle it; for the `f(void)` shape, give the function its real parameters | arity audit over all call sites; typed native thunks for the script engine's natives; a scan for `(void)` functions that read locals named after registers before assigning them |
| **Generated call glue that trusts the wrong declaration** | a script's flag setter got a huge flag id; a character stood in a T-pose (verified, 2026-10-16): the generator that builds typed call thunks for the script natives took the first declaration it found, often a stray `extern void f(void);`, so the native ran with no arguments and read leftover registers | build glue from the function's own definition, skip bodies the PC doesn't compile (GameCube `asm`), and list every function whose declarations disagree | the generator's own conflict list (72 natives had conflicting declarations) |
| **Evaluation order the C standard leaves open** | two calls with side effects inside one operator expression, such as `(rand() & 0xFFFF) \| (rand() << 16)`: C fixes no order; the GameCube compiler (MWCC) called the **right** operand first here, GCC evaluates binary operators **left to right**. The source matches byte for byte on the GameCube, yet the PC computes something else: every Pokémon's personality value had its two halves swapped, so the starter Espeon was redrawn twice where the console kept the first draw, the random-number sequence fell 4 draws behind the console's, and nature, gender, ability and shininess all came out differently (verified 2026-10-17 from the assembly and Dolphin's RNG state). **Function arguments are not affected:** GCC evaluates them right to left, as MWCC does (verified with a small test program and three `f(x * rand(), y * rand(), z * rand())` sites in the assembly). `\|\|`, `&&`, `?:` and `,` are sequenced and safe | in the PC port, split the expression into sequenced statements in the console's order, read from the assembly (`bl` order) | grep operator expressions holding two calls to one side-effecting function (a regex sweep of the game, HSD, MusyX and SDK code on 2026-10-17 found only the two personality sites; it does not catch two *different* functions that share state, such as two readers of one stream) |
| **Functions written `void` whose result is used** | text control codes that return nothing in the PC port: names and numbers vanish (verified) | restore the return value (verified from the assembly) | void-result checker |
| **Signed values turned into pointers** | a pointer kept in a signed integer sign-extends on a 64-bit host | cast through `u32` / `uintptr_t` | signed-to-pointer scan |
| **GameCube-only memory checks** | `if (p <= 0x80000000)` meaning "not in main memory" is false for every PC address | replace with the intent (`p == NULL`) under `TARGET_PC` | grep for 0x80000000 / 0x81800000 comparisons |
| **Multi-byte constants read as bytes** | a 4-byte constant read byte by byte gives the controller port masks in the wrong order: START ignored (verified) | define the constant so its bytes match in the PC port | review of byte reads of constants |
| **Data defined at one width, read at another** | the decompiled data files keep many tables as raw bytes in GameCube order, or as u32 words where the code reads u16 halves (or one wide copy into a byte list). Harmless on the GameCube, byte- or half-swapped in the PC port: Protect failed half the time on its first use (a u16 chance table written as u32), status lengths came out 0 or random 0-255 (s32 {min, max} pairs left as bytes), lowered accuracy raised it (byte pairs converted as u16), Pickup always gave the first item, EV gains and many menu ids were byte-swapped (verified from code, 2026-10-18); the Relic Stone skipped every purification because a two-pair {group, index} u16 table was generated as u32 words, so the ceremony's effect never loaded (verified from a trace, 2026-10-29), and its one-pair sibling, declared as a single u32, made every later step of the ceremony skip a short pose and its fade-in, about 120 frames each (2026-10-29). A search for such casts has to match both spellings, `(u16*)lbl_x` and `(u16*)&lbl_x`: the first scan matched only the first and missed the sibling. Watch for tables copied whole in u32 pieces and then read as u16 or bytes, and for pointers to byte pairs typed `u16*`: the copy width says nothing about the element width | give the PC the table at the width the code reads, under `TARGET_PC` (typed values, or the same bytes in PC order); for generated data, an explicit type or record layout per table, and plain bytes where the code reads bytes | a checker that works out each table's PC element width (from the PC definition or the generated data) and compares it with every read the PC compiles: scalar casts, declarations read by value, struct views, wide stores, big-endian accessor reads; flag mixed read widths as "a copy, then a read" |
| **Output lists of pointers at the wrong cell size** | a helper fills a caller's array with pointers through `void**` (8 bytes each on x64) while the caller declares the array as `u32[N]` (the GameCube's 4-byte pointers): each pointer fills two cells, every second entry reads 0, and the stores run past the array. In a battle AI that scores each candidate with one random draw, a skipped candidate is one draw fewer, so every later roll in the battle drifts by one (verified, 2026-10-29). Fixing one caller isn't enough: the same helper often has several callers, and only some had been fixed | keep one convention per list (here 4-byte cells, which the sort and the readers use) and convert at the helper's boundary under `TARGET_PC` | list every function with a `void**` out-parameter and check each caller's array type; also functions declared `void` whose callers use the result (the GameCube body left a count in r3) |
| **Byte pokes into 32-bit colours** | a colour built as `((u8*)&rgba)[3] = alpha` lands in the red channel in the PC port: opaque cyan stripes on every message window (verified). The reverse too: a colour value stored as a native u32 into a field the code reads as GXColor bytes (r, g, b, a): the name entry's white balls drew opaque cyan, and a fainted Pokémon's 50% grey party panel drew half-transparent red (verified against Dolphin, 2026-10-29); white `0xFFFFFFFF`, the usual value, reads the same either way, so only the rare colours show it. The same through a union of a u32 and four u8 channels: Battle Mode's "O.K.? / YES / CHANGE" box drew opaque with bright cyan scanlines until 2026-11-15 (`fn_80063AD4`; verified against the European disc in Dolphin) | build the colour by value | grep for `((u8*)colors)[n]`, and for unions whose u8 channels are written before the u32 is used |
| **Integer division by zero** | the GameCube's PowerPC doesn't trap on a zero divisor (`divw` gives 0, or -1 for a negative dividend; Dolphin matches), so game code that divides by a value that can be 0 runs on happily there; on x86 the same division raises an exception and the game dies. Seen in a party menu's HP bar (`(cur × width + max − 1) / max` with a max HP of 0, opened right after a purification; verified from the crash, 2026-10-29) | guard that division under `TARGET_PC` with the PowerPC's result (0, or -1 for a negative dividend), and log the case once so the cause of the zero can be traced | an exception handler that names the function (the crash log's `0xC0000094` with addr2line); a source scan for divisions by a struct field or a call result |
| **Textures the CPU rewrites** | the game writes into a texture on the CPU (the text glyph atlas, rebuilt every frame) and relies on the GameCube's cache flush; a PC graphics layer that caches textures keeps serving the first upload: every window showed the first message's letters, jumbled (verified) | the GameCube invalidates its texture cache after a CPU write; the PC renderer needs a new data version or a re-hash at that point: bump the texture's data version on every unlock (one place: the texture unlock function) | none yet; look for CPU writes between a texture lock and unlock |
| **Hand-written externs that disagree with the real prototype** | decompiled files often declare a callee themselves with `u32` stand-ins; on x86-64 the 5th and later arguments go on the stack, so a `u32` 0 passed where the callee expects a pointer or a 64-bit value arrives with garbage in its upper half: the audio library called a "callback" at 0x10000000000 when the opening movie's sound streamed (verified) | under `TARGET_PC`, declare the callee with its real signature (or include its header) | compare every hand-written `extern` against the defining header's prototype (pointer / 64-bit / float parameters, and anything past the 4th argument) |
| **Floats passed through empty-parameter declarations** | a decompiled file declares a callee as `void f();` (arguments unspecified) and calls it with a `float`. C then passes the float as a `double`. The PowerPC holds both in the same float register, so the console never shows it; on x86-64 the callee reads a float from the low half of the double's bits, a garbage number. A move's feathers were drawn either all at their start point or all at their end point, flipping at random every frame, because their place on the curve arrived as garbage and was clamped to 0 or 1 (verified, 2026-11-21) | a real prototype under `TARGET_PC`, every empty-parameter declaration hidden in the PC port | GCC's `-Wdouble-promotion` does **not** catch it (it warns for variadic calls only; verified); scan instead for `f();` declarations in files that call `f`, where `f`'s definition takes a float and no prototype is in scope. Symptoms: values that snap to the ends of their range, or random jumps where the console moves smoothly |
| **A record converted on one side only** | a runtime record the game passes between functions (here a menu window's argument block) is kept in the GameCube layout in the PC port, with its pointers as 32-bit slots, and the code that fills it was converted; but some readers still declare those fields as native pointers, so an 8-byte read takes two slots at once or, after alignment padding, a slot further on: opening a shop crashed reading address 0 (the +0x14 slot read from +0x20), and the quantity entry and the list selection read and wrote the wrong place (verified) | declare the reader's fields as the same 32-bit slots (`PTR32_FIELD`, read with `P32`; raw offsets with `PTR32_AT`), which compile to the original pointers on the GameCube | grep the readers of every converted record: `**(T**)ctx`, `*(void**)ctx` and structs with native pointer fields that view the same block; log the block's raw words at the crash to see the layout. The writer side has the same trap: a menu's argument block built as a local C struct with a native pointer member (`u32* result`, `s32* values`) moves every later field by 4 bytes, and the window's draw callbacks, which read the GameCube offsets, see padding. Three crashes from one night of replays (a shop's quantity window, the bag's give-item confirm, a summary screen's next/previous callback slot read as an 8-byte pointer); grep for local structs passed to `menuOpenCustom` that hold pointer members. The reverse also happens: a **native** struct (one the PC keeps with 8-byte pointers, here the spline object) read at the GameCube's raw offsets: the free routine took its two memory handles from `+0x20` / `+0x22`, which in the PC port fall inside a pointer, so nothing was freed and the game heap ran out a few hundred frames into a menu that builds 8 curves a frame (verified). Search for raw `*(u16*)(ptr + 0x..)` reads of structs that have a C definition, and read the fields instead |
| **A stack buffer smaller than what is copied into it** | a decompiled function declares a local buffer at the size that byte-matches (here `u8 copy[0x130]`) but hands it to a copy routine that writes a whole record (0x138 bytes); on the GameCube the frame's layout absorbs the 8-byte overrun, in the PC port it overwrites the caller's loop counter, so the next call gets a junk argument: the Colosseum's party-rules check hit its "invalid argument" assert before the first Realgam Tower battle (verified) | under `TARGET_PC`, size the buffer to what the copy writes | grep local buffers handed to whole-record copies (`pokemonBiosCopy`, `memcpy` of a struct) and compare their declared size with the copy's. A variant: a local `u32 list[6]` (or a byte buffer) handed to a function that fills it with **pointers**: in the PC port six 8-byte pointers overrun it and overwrite the saved registers, so the crash shows up later in the caller with a register at 0 (Roar's forced switch, verified); grep for callees taking `void**` and compare the caller's array type |
| **A list walk that reads its link natively** | a GameCube-layout linked list (a window's sprites: head at window +0x1C, each next link at +0) is walked with `node = *(u8**)node`; the head is converted but the 8-byte link read takes the next field as its high half: the party-check window crashed in its first loop (verified) | read every link as a 32-bit slot (one macro per file keeps the loops readable), as the list's own search routine does | grep for `= *(void**)node` / `*(u8**)node` style walks and compare them with how the list's owner reads its links |
| **An assert message read by GameCube offsets** | a function takes its assert texts as `base + offset` from one string label; in the PC port each generated label is its own array and the labels can be laid out in another order, so the printed text belongs to a different assert (here 16 characters into an unrelated one): the message misleads, the condition is real (verified) | find the failing check by its line number and the caller (a PC-only log in `__assert` printing file, line and `__builtin_return_address(0)`), not by its text | when an assert's text doesn't fit its place, map the exe's symbol addresses (`nm`) and compute where `base + offset` lands. The same happens to **whole tables**: a unit's constant pool is addressed from one label (`lbl_80267EA8 + 0x4EC`), and the offsets reach into the next labels. In the PC port each label is its own array, and may be converted per record at a grid the reader doesn't use, so a sprite search got a junk id and the rules screens wrote to address 0x4C (verified). Fix: rebuild the stretch the reader uses at the console's offsets (undo the record conversion to get the disc bytes, then write each field at its own width), and point the reader at that copy in the PC port; check the disc bytes for where each table ends, since neighbouring tables can use different grids |
| **Units kept out of the link only by a compile failure** | a header handed over to a library header that can't be included (it includes `types.h` without its directory), so 18 units stopped at a fatal error with no `error:` lines; the GBA link's uploader functions became empty stubs and the "no GBA plugged in" path waited forever (verified). Fixing the header made the SDK's GBA hardware driver compile too, which would have replaced the "nothing plugged in" stub, since the linker takes a library's symbol only when no object defines it | fix the header, and leave out on purpose what must stay out (`#ifndef TARGET_PC` around the hardware driver, with a note naming its replacement) | read the compile-failure list after every header change, including entries with "0 errors" (a fatal error); `nm` the exe for which copy of a replaced function was linked |
| **Library tables sized for the GameCube** | a library's static tables are sized in bytes for 4-byte pointers; in the PC port the same byte size holds half the entries, and inserts overflow into the next table: every music note failed to find its sound macro and the title stayed silent (verified) | give the PC its own tables sized by entry count (`[N]` of the native struct), under `TARGET_PC` | grep for tables declared by byte size (`[0x800 / 8]`-style) whose entries contain pointers |
| **Thread-layer state that assumes one caller** | the GameCube runs some engine threads from an interrupt, on whatever stack was interrupted; a PC replacement that keeps one global "scheduler" context breaks when that happens: a thread yielded into another thread's stack, the scheduler's idea of the current thread went stale, and a movie decoder ran past its own suspend and read past the movie (verified) | keep such state per thread (each thread returns to the context that ran it); decide "inside a thread" from the running context, not a global | an assert at every context switch that the running stack belongs to the thread the scheduler thinks is current (cheap, silent until it fires) |
| **Game callbacks on a real host thread** | the audio mixer runs the game's stream callbacks on its own OS thread; a callback that sends a message wakes a game thread, and a scheduler that switches right away does it on the wrong OS thread: from then on stacks are saved under the wrong thread and threads resume in the wrong places, here a movie decoder past its own suspend, about one boot in three (verified with an event trace; it happened in every boot, the crash only when the timing was unlucky) | only the game's OS thread switches; a wake from any other thread leaves a pending reschedule that the game thread takes at its next interrupt point (what the console does when the interrupt ends) | a one-time log line whenever another OS thread wakes or blocks a game thread |

But the render thread runs its presenter again right after the drain, so an in-between picture can be submitted with buffers that are being freed (verified 2026-11-20: NVIDIA's Vulkan driver read freed memory; a test that resizes the window every few frames crashed after 12 resizes, and after the fix ran 5,674 without one) | give the presenter a pause the surface code holds for the whole change; make sure a presenter call already running finishes before the change starts (a sync item the render thread takes only between presenter calls does that) | a crash stack through the present path right after a "frame buffers resized" log line; reproduce with a test switch that resizes the window every few frames while the presenter runs |

## 3. Tools and what each is for

- **Safe runner:** every heavy build and boot goes through it: a machine-wide lock (one heavy job at a
  time), a time limit that kills the whole process tree, a memory cap, low priority. Added after several builds and
  boots at once froze the machine (verified).
- **The gate** (one script): full GameCube build, all checksums, the per-function match report with "no score went
  down", the PC compile probe with 0 errors and the slot-walk checker. Nothing is committed without it.
- **Data generator:** turns the original program's data and the room modules' data into
  C at build time, from the player's own disc image; converts typed fields to native order, relocates pointers, lists
  every symbol it is unsure about. The output never enters version control. **The "unsure" list is a bug list:** a
  table left as a raw big-endian copy is right only while every reader takes it byte by byte. One such table, a
  two-record list that a native u16 read searches, made every item chosen in a battle fail without an error (the
  kind read 0x1200 instead of 0x12); a replay showed only "the ball was never thrown". Type each unsure table its
  readers use with multi-byte reads. An audit of the whole list (453 non-zero tables, 58 named by compiled code)
  found six more: menu window lists walked as native records (a likely crash in one menu), three screen positions
  read byte-swapped, and a pointer table read as native 8-byte pointers with a loop that would overrun its buffer.
  Method that worked: the PC binary's line table for "really compiled", then follow every variable assigned from
  each table to its reads. A **typed** table is only as good as its struct: fields the struct calls
  padding stay big-endian too (the weather table named only its first two fields, so its three battle message ids
  were left as raw bytes; verified from the generated table, now typed). A sweep for padding whose bytes read
  `0, 0, x, y` in every record (a big-endian word with a small value) finds such fields; check each one's readers.
- **Stub generator** (part of the first-link script): every function the port lacks becomes a stub that logs its first
  call and caller, so the game keeps running and the log says what to write next.
- **One definition per symbol:** the matching build compiles some files several times; the PC link
  keeps the copy owned by the unit whose address range holds the symbol.
- **PC compile probe:** compiles every unit in the PC configuration and counts errors; part of the gate.
- **Diagnostics in the PC build:** scripted controller input (`ORRE_PAD_SCRIPT=frame:BUTTON,...`), frame dumps to PNG
  at chosen frames (`ORRE_DUMP_FRAMES`), a switch that skips movies so a run can get past a broken one
  (`ORRE_SKIP_MOVIES`), an audio level meter, a watchdog, a frame log, a crash handler that prints a
  decodable call stack, the game's own debug log echoed to the console, and a few PC-only log lines at room changes
  and battle start / end.
- **The platform layer underneath (what replaces the console):**
  - **Memory map:** the game keeps addresses in 32-bit slots, so everything it can see lives below 4 GB: main memory
    reserved at its GameCube address (0x80000000) before the graphics driver starts, the executable linked at a fixed
    low address without address randomisation, and a separate low region for buffers the port hands to the game.
    A start-up check (`--check`) verifies each piece.
  - **Threads on fibres:** the SDK's threads become cooperative fibres on one host thread, scheduled by the original
    rules (highest priority runs, a woken higher-priority thread takes over at once). Real host threads (audio, disc,
    graphics workers) never run game code; they post "interrupts" that the game thread takes at points where
    interrupts are enabled. The engine's own thread layer (which switched register files in assembly) runs on fibres
    too.
  - **Graphics and windowing:** an existing GX-on-WebGPU layer (Aurora) with SDL3 underneath; the port adds what it
    lacks for this game (fixed-address main memory, disc and memory-card callbacks delivered to the game thread, a
    virtual controller for scripted input, movie drawing) and keeps those changes as separate, documented commits.
- **Finding timing-dependent bugs:** printing changes the timing, and a crash seen one run in three can vanish under
  probes. What worked: a silent in-memory ring of the last few dozen scheduler switches plus a cheap consistency check
  that dumps the ring only when it fails; short repeated runs (30 seconds) with the same settings as the run that
  crashed; and judging a fix by the crash rate over several runs, labelled "likely" until it has held for a while.
- **A log file for every run, with a build stamp:** testers launch the port by hand and the console vanishes on a
  crash, so every run writes its own log file (a copy of everything printed, flushed as it goes, the newest 20 kept),
  and the first line, the window title and every crash report name the exact build (commit, uncommitted changes, build
  time). The crash report also gives the last room and frame. Asking "which build, where were you" stops being guesswork.
- **Prototype scanner:** compares every hand-written `extern` in the decompiled code with the real prototype of the
  platform library it calls (pointer / 64-bit / float parameters, anything past the 4th argument). It found the two
  stack-argument crashes of this kind and one more waiting to happen; simple text matching, so it has false positives
  inside console-only `#if` blocks. It now compares against the decompiled code's own
  definitions too, skips console-only blocks, and ends with a short list of declarations that pass fewer arguments
  than the function takes and are actually called (the callee then reads leftover registers): 6 of 170 findings.
- **Audio dumps and comparison:** the port writes its mixed output to a WAV file on request, and a small tool lines it
  up with the emulator's audio dump by loudness envelope, then reports the offset, the level difference and clipping
  on both sides, and the moments where they differ most (where to listen). A sound that plays on one side only shows
  up as a large local difference.
- **Repeatable routes:** scripted button sequences that must reach a given screen (title, memory card, top menu, new
  game) with pass / fail from the log, re-run on every new build as regression checks.
- **Dolphin comparison:** the same moment in the emulator and the port, side by side (scripted Dolphin with memory
  watches for the differential tests), and a list of "eyes needed" checks for a human.

## 4. Working in parallel

- **Parallel workers with strict file ownership:** the work splits into areas (the game code on the boot path, the
  model / rendering library, the platform layer, documentation, data formats and testing); each worker edits only the
  files of its area, and anything else goes to the owner as a request.
- **One integrator:** branches are merged by one integrator only, without rewriting history, and every merge runs the
  gate.
- **One control document** holds only the current state: each area's status, the next tasks, what needs a human
  decision. History moves to an archive and decisions to a log, so the document stays short.
- **One heavy job at a time** across all workers (the safe runner's lock), with a time limit and a memory cap.
- **What worked:** small verified commits with the gate; a crash → log → fix → rerun loop of minutes; giving a bug to
  the worker that found it, with temporary access to the files it needs; documentation read ahead of the boot (it
  found the name-entry route and the yes / no default before the boot got there); turning each boot sequence into a
  regression route.
- **What didn't:** several heavy jobs at once (the machine froze); trusting a passing build as proof of matching (the
  build always matches because unmatched functions fall back to the original assembly; only the per-function report
  counts); quoting a tool's numbers without checking its flags.

## 5. Pitfalls and lessons

- Keep the original layout and change only how it is read: converting a record to a native struct means finding every
  private view of it, and there are often a dozen.
- When a value looks "uninitialised" in matched code, it is a register: trace it to the caller's assembly and give the
  PC the same value.
- A checker's false positives cost trust: exclude pointer variables from "past the end" checks.
- Shell here-documents can mangle escapes (`\n`) in generated C strings; write such edits with a real editor or a
  script file.
- Log lines at room changes and battle boundaries make every later boot run easy to read.
- A MinGW-built executable that links the C++ / thread runtime dynamically picks up whichever runtime DLLs come first
  in PATH; a different toolchain's copy fails at start (0xC0000139). Ship the matching `libstdc++`, `libwinpthread`
  and `libgcc_s` DLLs next to the executable, or link them statically.
- A game's own error message is not always a port bug: "can't open" lines for sound archives turned out to be second
  opens of archives that were already loaded (the game logs the same on the console, likely). Probe the function's
  early returns before fixing anything.
- A program that restarts itself must not hand its own stdout / stderr to the new copy when they are a log pipe: the
  new copy writes into a pipe nobody reads once the old one is gone, and after the pipe's buffer (64 KB on Windows)
  fills, its writes block. Start the new copy with null output (it writes its own log), create the pipe
  non-inheritable, and never hold a lock across a console write that a shutdown path waits on. Sign: each restarted
  run's log stops mid-line at about 64 KB, and its next restart freezes.
- Run the port from a scratch folder, not the repository, so frame dumps and logs never get committed; the folder
  then needs the executable's libraries on the search path.
- Debug shortcuts skip setup the game does along the normal path. A save-state style "checkpoint" loaded right after
  boot skipped the title screen, which loads sound groups the battles need, and the battle lost its cries. Let
  shortcuts wait until the normal boot has passed the screens that set things up, and compare a failing run's path
  with a working one's before suspecting the code.
- A game's warning can be routine: "Forced termination SE" in this game's sound status check also appears when an
  effect simply ended. Add your own log at the point of failure (here: the sound library's start function saying
  why an effect did not start) instead of reading meaning into the game's messages.
- Changing the memory layout changes what is left over, not only where things are: moving to the console's own arena
  bounds left the system heap with the console's free space (2.6 MB instead of 8.4 MB). Count heap peaks and failed
  allocations right after such a change; a structure that grew in the PC port fails there first.
- Mark test windows: start automated runs minimized and give test builds a distinct title, so nobody plays the
  wrong window.
- Replaying an emulator recording on the port: an emulator probe that samples the controller latch once per frame does
  not show what the game read. The console polls the pad more than once per frame and the game copies the latest
  poll at a point that moves from frame to frame, so a fixed "latch at frame f" rule is wrong on a few percent of
  frames. Because the game quantises the stick (dead zone, clamp), most of those errors are invisible, until one
  lands on a boundary and changes a step by a fraction of a unit; a turn later the character is somewhere else.
  Reconstruct each read instead: replay the game's own stick filter and clamp (in single precision) over the probe's
  post-read values and keep the candidate that reproduces them. Before calling a movement difference a port bug,
  check the per-frame stick the game used on both sides, not only the raw input.
- A deterministic replay clock that only hands disc reads over at a screen refresh breaks every busy wait: this game's
  archive loader polls the drive in a tight loop for each archive's table of contents (a few hundred bytes, no seek),
  which the console finishes inside the same refresh. Rounded up to the next refresh, the wait held the frame across
  it and the game logic fell a refresh behind (24 times in one battle, and the battle's random picks parted). Give the
  replay clock a sense of time inside a refresh (here: the share of a refresh's interrupt points used so far) and
  finish reads part-way through it. Log every refresh that comes while the frame is not in its own retrace wait,
  with the stack: it names the wait at once.
- Tuning the replay's input timing per room hides model errors: a "this room needs 0 extra frames" value can be
  standing in for a stall the model got wrong. When a model fix makes a room worse, re-measure that room's input
  calibration before reverting the fix.
- When the reference recordings come from Dolphin, model disc seeks the way Dolphin's code actually computes them, not
  the way its comments describe them. Dolphin's read scheduler divides emulated ticks by ticks per second in
  integers before the rotation formula, so every seek starts from the disc angle of a whole second (with 28.5 turns a
  second, 0 or half a turn). With that rule on the console's clock and one fitted constant (the emulated time of the
  first video retrace), the drive model put 81 of 82 seeks of a whole play session in the field the emulator
  recorded; with true fractional time it managed 27 to 43. Read the source line by line for integer arithmetic.
- An emulator's per-frame read log records each read's end at the first poll that saw it, so recorded lengths come
  out one frame long about two times in three (compared with a full register-level capture of the same session).
  Calibrations built on those ends absorb the error, so correcting the ends alone makes things worse until the
  calibrations are redone.
- A getter that returns a pointer to either a live record or a constant from the executable needs both in the same
  byte order. This game's Shadow-move view hands back two fixed four-byte move records (Shadow Rush and the "?" move)
  instead of a snagged Pokémon's own moves; the live records are converted to native order with the save, the
  constants were the executable's big-endian bytes, and every reader takes the record as a native struct. The move
  ids came out as 0x6401 / 0x6501, so a snagged Shadow Pokémon's move menu was empty. Look for getters whose return
  can point into data the port loads raw, and give them native copies.
- A sound effect restarted on the frame the previous one ends: if the port mixes audio ahead inside the start call
  (to model the console's output latency), the old voice can end, and the game's sound callback release the entry,
  before the game has stored the new handle. Model the latency in the mixer instead (each new voice waits a few
  blocks before it plays), so nothing that happens after the call runs before it.
- A picture whose shape reaches the edge of its canvas shows a hard, flickering edge once its box is rotated or moved
  by fractions of a pixel: the box's own edge cuts the shape with no smoothing, and a texture sampler set to repeat
  also blends in the opposite edge. Seen on a launcher's swaying disc (a thin flat strip flickering at the top of
  its rim). Give such pictures a few transparent pixels of margin (and draw their boxes larger by the same ratio),
  and clamp the UI's texture sampler unless something really tiles.
- A text field that checks typed characters against a list silently drops whatever an input method (IME) commits:
  kana, kanji and full-width letters arrive as ordinary text input and simply fail the check, with no error anywhere
  (verified: a naming keyboard took only printable ASCII and its own pages). Ask the font code "can this be drawn?"
  instead of keeping a list, and test with an IME early.
- To draw an IME's composition and candidate list inside the game, SDL 3 needs `SDL_HINT_IME_IMPLEMENTED_UI`. On
  Windows SDL reads that hint once, the first time its IME support starts (verified in SDL 3.4's source), so it cannot
  be switched on only for one screen; on Linux (IBus, fcitx) it is read live. If other text fields in the same window
  rely on the system's own IME windows, set the hint at start-up and route the window's IME messages per moment (to
  SDL when the game draws them, to Windows' default handling otherwise). Only SDL's Windows backend sends candidate
  lists; its selected index counts across the whole list while the strings are one page.
- The game's texture records come from a fixed pool: a port that makes a texture per small UI text runs out after a
  handful (the texts silently stop drawing). Pack such texts into one atlas texture and crop it with sprite records.
- A debug build's automated runs can't type with a real IME; inject the events the SDL layer would produce (composition,
  candidates, commit, keys) into the same input layer on chosen frames, and dump frames to check each state.
- **A GPU readback callback must never drop the last reference to its buffer** (verified with Dawn's WebGPU, 2026):
  some Dawn versions release the buffer's lock after freeing the buffer when the callback held the last reference, a
  rare write into freed memory that crashes about one start in ten with frame dumps on. Keep readback buffers in a
  pool that outlives the callback, or release them later outside any callback, until the library carries the fix.
- **Interpolated frames (frame smoothing) need identity, not draw order:** match each piece between two game steps by
  what it is (its model, pass, draw, or a name the game code passes along), blend only what moves steadily, and show
  the newest step whole for anything that appears, vanishes, swaps pictures or jumps; matching 2D by draw order is
  what makes bars drift.
- **Even inside a named piece, a draw that comes and goes shifts every draw after it** (verified, 2026): draws inside
  one piece were paired by their number. A blinking cursor whose alpha reaches 0 isn't drawn at all in that step,
  so every later draw paired with its neighbour. Name-field dashes jumped halfway to the next dash twice a second,
  and a help text's letters blended into each other's places when the text changed. A jump guard doesn't catch it,
  because neighbours are close. The fix is to count each piece's draws in both steps, and when the counts differ, show
  that piece's newest step instead of blending. Find it with full-size dumps of the step and in-between pictures at
  the player's own resolution. At a small size the shift can be too small to notice.

## 6. Case study: the game's own bitmap fonts at high resolution

GameCube games usually draw text from small bitmap fonts made for a 640 x 480 picture. At 1440p or 4K those letters
come out blurry when filtered, or blocky when not. This section
describes how the game draws its text, what matching open fonts showed, and how characters the fonts lack can be
added; it does not cover redrawing the game's own letters.

### How the game draws text (verified from the code)

- Five fonts, each a set of 4-bit pictures (16 grey levels), one picture per character. Every picture has a width and
  height and sits in a fixed-height cell, with a vertical offset.
- The CPU builds each line of text letter by letter into a 512 x 512 4-bit texture. There are two of them, swapped
  every frame.
- The GPU then draws quads that sample that texture with normalised coordinates (0 to 1).
- Layout comes entirely from the pictures' sizes: advance width, line wrapping and centring.

That last point means a character's picture can be swapped or added without changing the layout, as long as each
character keeps its size.

### Matching open fonts (measured)

One approach is to draw every character from open-licence fonts chosen to look like each game font. The fonts were
measured and tuned against the game's own pictures:
- **Size:** each font was sized so its capital height equals the game's 'H'.
- **Placement:** each letter was placed in the game's own ink box (the part of the cell its picture covers), so
  spacing and baseline stayed the game's.
- **Look:** weight, width and synthetic emboldening were tuned per font with a scorer that lays the original and the
  candidate side by side on a line.

The result was close: ink coverage was within 92-106% of the originals and edges within a pixel. But the scores
plateaued well short of identical (about 0.79-0.90 on a 0-1 similarity scale), and side by side the letters were
plainly a different typeface. So the open fonts are used only for characters the game's fonts don't
have (below).

**A measuring lesson:** read a font's capital height and baseline from rows that are at least half dark (grey level 8
of 15 or more). Counting the faint anti-aliased edge rows made one font a whole size too big and moved its baseline by
a pixel.


### Characters the game's fonts don't have (verified in game)

A translation needs letters the fonts lack, for example š, ŵ and Ť in Latin Extended-A. The game draws a white box
for a missing character. The port hooks the glyph lookup's "not found" path and returns a glyph record laid out
exactly like the game's own, in a small extra bank the port owns. Its picture comes from the open font chosen for that
game font, sized to the game's capital height and placed on its baseline. The game then measures, wraps and draws it
like any other letter.

To test all of this without a translation, the port has a **pseudo language**: the game's English with each letter
swapped for an accented look-alike of the same length. Some look-alikes are in the fonts and some aren't, so missing
characters show up in real dialogue and menus.



## 7. What carries over to XD

XD runs on the same engine layers (the Dolphin SDK, the HSD model library, the MusyX audio library and the developer's
own framework), so the families above, the data generator, the gate and the diagnostics should carry over unchanged
(likely). Expect XD-specific work where its code differs: a rewritten script engine (its values carry their own types,
so the bridge for its native functions is different), its own tables and save layout, and its battle AI extensions.
